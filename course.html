Safe Native Tooling for LLM Agents in Modern C++

Build agent-toolbox, a C++20 service that gives an LLM agent a default-deny, audited, contained tool boundary.

See pricing & enroll Basic HTML

Course promise

You build—not merely discuss—a native tool boundary for an LLM agent. The finished agent-toolbox service admits bounded JSON requests, applies explicit capability grants, routes every call through a default-deny gateway, performs contained file operations, executes one hash-pinned external binary without a shell, indexes Markdown notes with SQLite FTS5, and writes durable audit records.

The course keeps three claims separate: language safety practices (value types, ownership, RAII, warnings, sanitizers, tests); application security controls (strict admission, authority, path containment, pinning, limits, audit); and operating-system isolation, which is outside the completed reference boundary and treated as a production-hardening extension.

Format

14 private one-on-one sessions, 90 minutes each, plus a capstone defense. Each session: a retrieval quiz and review, a concept demonstration tied to a concrete failure mode, guided implementation in agent-toolbox, an adversarial test with evidence capture, and a homework contract. A lesson is complete only when its acceptance gate passes; attendance alone does not count.

Audience & prerequisites

For developers comfortable with functions, classes/structs, pointers, references, standard containers, and basic command-line Git. No machine-learning background is required. A pre-course diagnostic identifies anyone who needs a C++ ownership, filesystem, or command-line refresher.

  • Linux or WSL (macOS works for most concepts but is not the qualification target)
  • GCC 11+ or Clang 14+
  • CMake 3.24+, Ninja, Git, pkg-config
  • SQLite3/FTS5, json-c, and OpenSSL development packages

Measurable outcomes

By the end, you can:

  1. Build a multi-target C++20 project using CMake presets and interface targets.
  2. Treat warnings, ASan, UBSan, CTest, and CI as executable quality gates.
  3. Model tool contracts so zero/default state denies rather than permits.
  4. Own polymorphic runners safely and reject duplicate registrations.
  5. Prove that delegated grants never exceed parent capabilities or budgets.
  6. Design one mandatory gateway for lookup, authority, validation, audit, and execution.
  7. Execute a qualified process without a shell and enforce timeout/output caps.
  8. Reject traversal, absolute paths, symlinks, unknown keys, and ambiguous JSON.
  9. Wrap SQLite, json-c, and OpenSSL C APIs in deterministic C++ ownership.
  10. Build literal FTS5 retrieval with bounded paging and JSON output.
  11. Pin an executable by SHA-256 and explain the remaining TOCTOU risk.
  12. Ship reproducible debug, release, and sanitizer qualification evidence.

The 14 lessons

  1. Project Layout & Modern CMake — Core, CLI and test targets with three presets that configure and build independently.
  2. Warnings, Sanitizers & Interface Targets — Reusable warning and sanitizer targets proven by detecting planted defects.
  3. Testing Without a Framework — A CHECK harness registered with CTest, covering every public function.
  4. Tool Contracts with Value Types — Request, result and grant types whose default construction denies.
  5. Interfaces, Ownership & Registry — A unique_ptr runner registry that rejects duplicate IDs.
  6. Default-Deny Authority & Grants — Capability and narrowing logic where every escalation case is denied.
  7. Gateway & Fail-Closed Audit — A central ToolGateway with no runner bypass and a durable preflight audit.
  8. Safe POSIX Process Execution — A no-shell executor tested for timeouts, output caps and process-tree kill.
  9. Hostile Input & Path Containment — Contained file runners that deny traversal and symlink attacks.
  10. SQLite RAII & Audit — Database, statement and transaction wrappers with rollback and bound-SQL tests.
  11. FTS5 Retrieval Index — Index, search and check mode with literal queries and stale-file checks.
  12. OpenSSL EVP Hash Pinning — A pin manifest that detects binary tampering before execution.
  13. Strict JSON Admission — A typed, bounded request parser that rejects the hostile corpus.
  14. CI, Qualification & Shipping — CLI/daemon split and a pinned CI workflow with the full matrix green.

Capstone: agent-toolbox

A C++20 core shared by a toolboxctl CLI and a line-oriented toolboxd daemon, with at least four qualified runners. Required properties include a typed request envelope with strict key and size limits, a default-deny gateway with explicit capability grants and child-grant narrowing, non-shell POSIX execution with a cleared environment and process-tree kill, canonical contained paths, a SHA-256 external-binary pin, an SQLite FTS5 notes index, preflight and completion audit records, debug/release/ASan+UBSan profiles with warnings-as-errors, at least 30 assertion checks with green CI, and a threat model that distinguishes application controls from OS sandboxing.

Assessment: lesson gates and lab records 30%, adversarial tests and threat reasoning 20%, capstone implementation and evidence 40%, final code review and oral defense 10%. Mandatory gates override the score: a submission cannot pass if it uses a shell for agent-controlled execution, defaults to allow, allows workspace escape, executes after a failed preflight audit, accepts duplicate JSON keys, lacks timeout/output limits, or fails warnings-as-errors, tests, or ASan/UBSan.

Validation evidence

The course’s reference implementation (agent-toolbox 1.0.0, course 2.0.0) was validated on 2026-10-12 from a fresh source-only copy with no pre-existing build directories:

  • 180 checks across 10 test executables, all passing (the capstone minimum is 30).
  • 10/10 CTest executables passed in GCC 14.2.0 debug and release, Clang 17.0.0 debug and release (warnings-as-errors), and a GCC ASan + UBSan build with no finding.
  • verify-hostile.sh rejected 22 of 22 hostile requests: duplicate keys, schema and type errors, numeric bounds, invalid numbers, trailing data, bad Unicode surrogates, absolute and parent paths, unknown tools, authority-budget excess, and more.
  • Executor tests show shell metacharacters stay literal, stdin is /dev/null, inherited descriptors are closed, the environment is cleared, timeouts and output floods are enforced, and descendant processes are terminated.
  • The student starter passed its smoke test in debug, release, and ASan + UBSan builds.

Honest limits: these results were run locally on Linux (GCC 14.2.0, Clang 17.0.0). A GitHub Actions workflow is included but has not yet been executed on GitHub.

Reviewed for security

An adversarial review on 2026-10-12 covered the curriculum claims, reference implementation, tests, examples, build, and packaging. It found and fixed 13 findings: 3 high, 8 medium, 2 low (for example, unpaired UTF-8 surrogates, symlinked parent directories, and proof that a failed preflight audit stops the effect).

Controls confirmed: deny is the zero/default decision; only qualified, enabled runners execute; capabilities match exact tool and operation identities; child grants cannot widen capability, depth, timeout, or output; unknown keys and duplicate JSON keys are rejected; absolute, parent, and symlink paths are denied; external execution never invokes a shell; environment, file descriptors, process lifetime, stdin, and output are bounded; the external binary must match a SHA-256 pin; preflight audit is durable before any side effect; SQLite inputs use bound parameters; and FTS5 receives literal queries.

7 remaining accepted risks (explicit non-goals or production-hardening work):

  1. Path validation and path use are separate operations; a same-privilege local process doing concurrent renames may exploit a TOCTOU window.
  2. Binary hashing and path-based execve are separate; production hardening should hash and execute the same descriptor.
  3. The executor provides no namespace, seccomp, cgroup, Landlock, Capsicum, container, or equivalent OS isolation.
  4. Post-fork setup assumes the single-threaded CLI/daemon model; a multithreaded host needs a dedicated subprocess helper or a carefully reviewed spawn design.
  5. A completion-audit failure cannot undo a side effect that already happened.
  6. Grants are instance-wide; remote multi-principal use requires authenticated principal-to-grant binding.
  7. toolboxd is a line protocol only: no network authentication, transport encryption, replay defense, or rate limiting.

Threat-model caveat

This is an instructional boundary, not a production sandbox. The reference implementation is qualified for the stated instructional Linux/WSL boundary only. Path and executable verify/use races (TOCTOU), a same-privilege local-attacker model, and missing namespace/seccomp/cgroup-style containment remain documented residual risks. Production deployment requires additional OS-level containment and independent review. Labs use disposable workspaces and non-privileged accounts, and the course does not authorize testing systems you do not own or have permission to assess.
